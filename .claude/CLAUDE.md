# DataMatch 프로젝트 최상위 지침

DataMatch는 사내 DB 거래 데이터를 자동으로 비교하는 웹 기반 프로그램이다. 개발은 **문서 기반 AI 에이전틱 개발 방식**으로 진행하며, 요구사항을 먼저 정의하고 확정된 문서를 기준으로 Task 단위로 구현한다.

전체 개발 프로세스와 문서 작성 규칙은 `docs/0-ai-dev-guide.md`를 따른다. 이 문서는 프로젝트의 최상위 지침이며, 모든 서브에이전트와 개발 스킬에 공통으로 적용한다.

## 1. 반드시 지켜야 할 지침

- 모든 응답과 개발 관련 문서는 한국어로 작성한다. 코드 식별자, 기술 용어, API 명칭 등은 영문을 사용할 수 있다.
- 오버엔지니어링을 금지한다. 요구사항을 충족하는 가장 단순하고 유지보수하기 쉬운 구조를 우선한다.
- PRD 및 설계 문서에 없는 기능을 임의로 추가하지 않는다.
- 확정된 요구사항과 제안 사항을 명확히 구분한다.
- 요구사항이 불명확하거나 문서 간 충돌이 발생하면 임의로 결정하지 않고 가정·미결 사항에 기록한다.
- 기존 코드와 문서를 수정할 때는 영향 범위를 먼저 확인한다.
- 관계없는 코드 수정이나 불필요한 리팩터링을 수행하지 않는다.
- 구현이 완료되면 관련 테스트를 수행하고, 검증되지 않은 작업은 완료 처리하지 않는다.

## 2. 프로젝트 개요

| 항목        | 내용                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------ |
| 프로젝트명  | DataMatch                                                                                  |
| 목적        | DB 거래 데이터 비교 업무 자동화                                                            |
| 주요 사용자 | 사내 개발자 및 운영 담당자                                                                 |
| 실행 환경   | 담당자 PC에서 로컬 실행하는 웹 애플리케이션                                                |
| 대상 DBMS   | Oracle                                                                                     |
| 백엔드      | Java / Spring Boot (제안, 기술 설계 단계에서 확정)                                         |
| 프론트엔드  | 기술 설계 단계에서 결정                                                                    |
| 주요 기능   | 환경 선택, 테이블·컬럼 선택, 거래번호 다건 비교, SafeDB 복호화, 결과 확인 및 엑셀 다운로드 |

세부 기능, 비교 규칙, 비기능 요구사항 및 MVP 범위는 `docs/1-PRD.md`를 기준으로 한다. 이 문서에서 상세 요구사항을 중복 정의하지 않는다.

## 4. 문서 목록

문서 경로는 저장소 루트를 기준으로 한다. 이미 작성된 PRD와 사용자 시나리오의 파일명은 유지하며, 이후 문서도 동일한 번호 체계를 사용한다.

| 문서            | 경로                             | 내용                                              | 상태       |
| --------------- | -------------------------------- | ------------------------------------------------- | ---------- |
| AI 개발 가이드  | `docs/0-ai-dev-guide.md`         | 개발 프로세스 및 공통 규칙                        | 작성됨     |
| PRD             | `docs/1-PRD.md`                  | 기능·비기능 요구사항, 비교 규칙, MVP 범위         | 확정(v1.3) |
| 사용자 시나리오 | `docs/2-user-scenario.md`        | 정상·예외 시나리오, 사용자 행동 및 시스템 반응    | 확정(v1.5) |
| 화면 정의서     | `docs/3-screen-specification.md` | 화면 구성, 와이어프레임, UI 동작 및 화면 전환     | 확정(v1.5) |
| 기술 설계서     | `docs/4-technical-design.md`     | 아키텍처, 기술 스택, DB 접근, API 및 구현 원칙    | 확정(v1.10) |
| 실행 계획       | `docs/5-plan.md`                 | 개발 Task, 선행 조건, 완료 기준 및 미결 결정 사항 | 확정(v1.4) |

별도 도메인 정의서, 구조 설계 원칙, 아키텍처 다이어그램, ERD, 스타일 가이드 문서는 기본 작성 대상에서 제외한다. 필요한 내용은 PRD, 화면 정의서 또는 기술 설계서에 통합한다.

신규 DB 테이블이 필요하면 ERD 및 `schema.sql`을 추가할 수 있다. 별도 API 계약이 필요하면 OpenAPI 명세를 생성할 수 있으며, 해당 문서는 기술 설계서를 기준으로 관리한다.

문서 상태는 `미작성`, `초안`, `검토 중`, `확정`으로 구분하고, 문서를 생성하거나 수정할 때 실제 상태와 버전을 갱신한다.

## 5. 문서 작성 공통 규칙

모든 문서는 제목 아래에 버전 이력과 변경 이력 표를 작성한다. 기존 문서를 수정하면 버전을 올리고 변경 내용을 기록한다. 표의 형식은 `docs/0-ai-dev-guide.md`를 따른다.

문서 내용은 제목과 문단 중심으로 작성한다. 문장마다 불필요하게 줄바꿈하지 않고, 관련된 내용을 하나의 문단으로 정리한다. 목록이나 표는 정보 구분이 필요한 경우에만 사용한다.

요구사항과 규칙은 최초 정의된 문서에서 관리하고, 다른 문서에서는 관련 ID로 참조한다. 문서 간 동일한 내용을 중복 정의하지 않는다.

주요 ID는 다음과 같이 관리한다.

| ID                                  | 의미                   |
| ----------------------------------- | ---------------------- |
| `G-xx`                              | 프로젝트 목표          |
| `FR-xx`                             | 기능 요구사항          |
| `NFR-xx`                            | 비기능 요구사항        |
| `R-xx`                              | 리스크                 |
| `SN-xx`                             | 사용자 시나리오        |
| `SC-xx`                             | 화면                   |
| `TD-xx`                             | 기술 설계 결정         |
| `SETUP-xx`, `DB-xx`, `BE-xx`, `FE-xx`, `INT-xx` | 개발 Task |
| `D-xx`                              | 개발 착수 전 결정 사항 |

확정되지 않은 요구사항은 각 문서 마지막의 '가정·미결 사항'에 기록한다. 기존 문서의 `PA-xx`, `SA-xx` 등도 유지하며 ID를 임의로 변경하거나 재사용하지 않는다.

문서를 수정하면 해당 문서를 참조하는 다른 문서와 불일치가 없는지 확인한다. 변경으로 영향을 받는 요구사항, 사용자 시나리오, 화면 및 Task가 있다면 함께 검토한다.

## 6. 개발 진행 원칙

개발은 `docs/5-plan.md`에 정의된 Task를 기준으로 수행한다. 실행 계획이 작성되기 전에는 임의로 본격적인 기능 개발을 시작하지 않는다.

Task를 수행할 때는 관련 PRD, 사용자 시나리오, 화면 정의서, 기술 설계서를 먼저 확인한다. 필요한 범위만 구현하고, 문서에 없는 기능이나 확장 기능을 임의로 추가하지 않는다.

백엔드와 프론트엔드는 필요에 따라 다음 스킬을 사용한다.

```text
/develop-backend BE-01
/develop-frontend FE-01
```

스킬 실행 전에는 해당 스킬이 실제로 존재하는지 확인한다. 스킬이 없거나 실행할 수 없으면 해당 사실을 보고하고 사용 가능한 개발 방식으로 진행한다.

각 Task는 요구사항 분석, 구현, 테스트, 결과 검증 순서로 진행한다. 테스트를 통과하고 완료 조건이 충족된 경우에만 실행 계획의 체크박스를 완료 처리한다.

서로 독립적인 Task는 병렬로 개발할 수 있다. 단, 같은 파일을 수정하거나 선행 의존성이 있는 Task는 순차적으로 처리하여 충돌을 방지한다.

## 7. 테스트 및 품질 관리

모든 핵심 기능은 정상 상황과 예외 상황을 함께 검증한다. 테스트 항목은 PRD의 기능 요구사항과 사용자 시나리오를 기준으로 작성한다.

백엔드는 핵심 비즈니스 로직과 오류 처리를 검증하고, 프론트엔드는 주요 사용자 동작과 입력 검증을 확인한다. 전체 기능 개발이 완료되면 통합 테스트 및 E2E 테스트를 수행한다.

테스트 도구는 프로젝트 기술 스택에 맞게 선택하며, 웹 화면의 E2E 검증은 브라우저 자동화 도구(Playwright MCP 등)로 수행하고 결과와 스크린샷을 `test/e2e/`에 저장한다.
