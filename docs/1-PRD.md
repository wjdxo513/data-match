## 1. 프로젝트 개요

사내 PG 거래 테스트케이스는 거래번호(PK)를 가진다. 같은 테이블에서 두 거래번호(A, B)의 행을 조회해, 사용자가 고른 컬럼 값을 자동으로 비교하고 차이를 보여주는 사내 도구다. A와 B는 같은 환경의 DB에서 조회하는 것이 기본이고, 테스트 DB와 운영 DB처럼 서로 다른 환경의 DB에서 조회해 비교할 수도 있다. SafeDB로 암호화된 CLOB 컬럼은 복호화한 뒤 JSON 필드 단위로 비교한다.

| 구분        | 내용                                                               |
| ----------- | ------------------------------------------------------------------ |
| 비교 단위   | 같은 테이블의 비교 키(기본 PK) 2건(A, B) 1:1 비교 (확정, v1.4)      |
| 비교 환경   | A쪽·B쪽 환경을 각각 지정한다. 같은 환경(예: 운영-운영)과 다른 환경(예: 테스트-운영) 모두 지원 (확정). 한 번 실행에서 A쪽 환경과 B쪽 환경은 각각 하나다 |
| 대상 DB     | Oracle. 개발·테스트·운영 DB에 직접 접속 (확정)                      |
| 사용자 인증 | 없음. 사용 이력 기록도 없음 (확정)                                  |
| 배포 형태   | 담당자 PC에서 로컬 실행하는 웹. 담당자 PC에서 각 DB와 SafeDB 서버에 접근 가능 (확정) |
| 구현 방향   | JDK 11 + Spring Boot 2.7.18 백엔드, React 프론트엔드 (확정, 기술 설계서 TD-01·TD-18) |

## 2. 개발 배경 및 문제점

- 거래 비교마다 SQL을 직접 작성해 조회하고 결과를 눈과 수작업으로 비교한다.
- 테이블과 컬럼이 바뀔 때마다 SQL을 새로 작성해야 한다.
- 암호화(SafeDB) 컬럼은 별도로 복호화한 뒤에야 비교할 수 있다.
- 수십~수백 건을 반복해서 비교하면 시간이 오래 걸리고 누락·오판 위험이 크다.

## 4. 주요 사용자 및 사용 시나리오

| 사용자        | 설명                                |
| ------------- | ----------------------------------- |
| 개발자        | 개발·테스트 DB에서 전환 전후 거래 결과를 비교 |
| 운영 담당자   | 운영 DB에서 두 거래의 데이터 차이를 확인   |

두 사용자 모두 같은 기능을 쓰며 권한 구분은 없다(확정).

**기본 시나리오**
1. A쪽 환경과 B쪽 환경(개발/테스트/운영)을 선택한다. 같은 환경이어도 되고 다른 환경이어도 된다.
2. 테이블을 검색해 선택한다. 단일 PK는 비교 키로 자동 인식되고, 복합 PK·PK 없음 테이블은 비교 키 컬럼을 고른다.
3. 비교할 컬럼을 체크박스로 고르고, 암호화 컬럼은 복호화로 지정(KDKEY 기본, 필요 시 PANEN)한다.
4. `거래번호A,거래번호B`를 한 줄씩 붙여넣는다.
5. 비교를 실행하고, 짝별 요약 목록에서 불일치 짝을 열어 컬럼·필드별 차이(빨간색)를 확인한다.
6. 필요하면 엑셀로 내려받는다.

## 5. 핵심 기능 요구사항

우선순위: P0 = MVP 필수, P1 = MVP 이후 확장.

| ID    | 기능명                    | 상세 설명                                                                                                                                                                                           | 우선순위 | 구분 |
| ----- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---- |
| FR-01 | 환경별 DB 연결            | 개발·테스트·운영 접속 정보를 환경별 properties로 정의하고(확정), 화면에서 A쪽 환경과 B쪽 환경을 각각 선택한다(PA-01). 두 환경이 같으면 연결 1개, 다르면 연결 2개를 쓴다. 화면에는 선택한 환경을 표시하고, 비밀번호는 화면에서 입력하지 않는다. | P0       | 확정 |
| FR-02 | 테이블 검색·선택          | 접속 계정이 조회할 수 있는 모든 스키마의 테이블을 대상으로 이름 검색과 자동완성을 제공한다. 동일 이름 구분을 위해 `스키마.테이블` 형태로 표시한다. 환경 간 비교 시 두 환경의 테이블 구조가 동일하므로(PA-15) 테이블·컬럼 정보는 A쪽 환경에서 조회한다. 복합 PK·PK 없음 테이블을 포함해 모든 테이블을 선택할 수 있으며, 짝을 찾을 때 쓰는 비교 키 컬럼은 FR-03에서 정한다(PA-10, PA-19).                              | P0       | 확정 |
| FR-03 | 컬럼 조회·선택            | 선택한 테이블의 컬럼명, 타입을 보여주고 체크박스로 비교 컬럼을 여러 개 선택한다. 모든 컬럼 타입을 선택할 수 있다(PA-11). 선택하지 않은 컬럼은 비교하지 않는다. 거래번호로 행을 찾을 비교 키 컬럼을 하나 고른다. 단일 PK이고 타입이 문자형·NUMBER이면 그 PK를 기본값으로 정하고, 복합 PK·PK 없음 테이블은 사용자가 직접 고른다. 비교 키 후보는 타입이 문자형·NUMBER인 컬럼이며(PA-19), 비교 키는 비교 컬럼과 별개로 사용한다(PA-10). 컬럼이 많은 테이블을 위해 컬럼 이름 검색과 전체 선택/해제를 제공한다.                                      | P0       | 확정 |
| FR-04 | 복호화 컬럼 지정          | 선택한 컬럼 중 CLOB 컬럼을 "SafeDB 복호화 대상"으로 지정한다. 컬럼별 정책은 KDKEY가 기본이고 PANEN으로 바꿀 수 있다.                                                                                   | P0       | 확정 |
| FR-05 | 거래번호 짝 입력          | 한 줄에 `거래번호A,거래번호B`(쉼표 또는 탭 구분)로 붙여넣거나 직접 입력한다. 위에서부터 순서대로 A1-B1, A2-B2처럼 짝을 맺는다. 거래번호A는 A쪽 환경 DB에서, 거래번호B는 B쪽 환경 DB에서 조회한다. 환경 간 비교에서는 환경마다 거래번호가 달라 두 번호를 모두 직접 입력한다. 형식 오류 줄(구분자 없음, 값 비어 있음, 한 줄에 구분자 2개 이상, NUMBER 비교 키에 숫자가 아닌 값(PA-19))은 줄 번호와 함께 알리고, 오류 줄이 하나라도 있으면 비교를 시작하지 않고 수정을 요구한다. 입력 건수가 최대치(1,000쌍)를 넘으면 전체를 거절하고 안내한다(PA-17).        | P0       | 확정 |
| FR-06 | 비교 실행·진행 표시       | 입력된 짝의 A·B 행을 비교 키로 조회해 선택 컬럼을 비교한다. 한 짝이 누락·키 중복이거나 복호화 오류여도 나머지 짝은 계속 처리한다. DB 연결 실패나 조회 타임아웃이 발생하면 전체 비교를 실패로 처리하고 안내한다(부분 결과 없음, PA-17). 비교 중에는 진행률(처리 건수/전체 건수)을 표시하고 중지 버튼을 제공한다. 중지하면 비교를 취소하고 결과를 만들지 않는다(PA-18). | P0       | 확정 |
| FR-07 | 복호화 및 JSON 필드 비교  | 복호화 대상 컬럼은 SafeDB로 복호화한 뒤 JSON을 필드 단위로 풀어 필드별로 비교한다. 환경 간 비교 시 A쪽·B쪽 데이터 모두 복호화할 수 있어야 한다(PA-14). 복호화 또는 JSON 해석에 실패한 컬럼은 "복호화 오류"로 표시하고 나머지는 계속 비교한다.                              | P0       | 확정 |

## 6. 데이터 비교 규칙 및 처리 방식

### 6.1 판정 규칙

| 대상     | 판정                | 조건                                                                                          | 구분 |
| -------- | ------------------- | --------------------------------------------------------------------------------------------- | ---- |
| 컬럼·필드 | 일치                | 값이 정확히 같거나, 양쪽 모두 NULL(미입력)                                                     | 확정 |
| 컬럼·필드 | 불일치              | 값이 다르다. 공백, 대소문자, 숫자 표기 형식 차이도 불일치로 본다. 한쪽만 NULL이어도 불일치     | 확정 |
| 컬럼     | 복호화 오류         | 복호화 또는 JSON 해석 실패                                                                     | 확정 |
| 짝       | 키 중복             | 비교 키로 조회한 A 또는 B 행이 2건 이상. 어느 쪽에서 몇 건 조회되었는지 표시하고 컬럼 비교를 하지 않는다. 누락보다 먼저 판정한다(PA-10) | 확정 |
| 짝       | 누락                | A 또는 B 행이 DB에 없음. 어느 쪽이 없는지 표시하고, 양쪽 모두 없으면 "A·B 모두 없음"으로 표시한다. 누락 짝은 컬럼 비교를 하지 않는다.         | 확정 |
| 짝       | 불일치              | 비교 컬럼·필드 중 하나라도 불일치이거나 복호화 오류가 있음. 사유를 함께 표시한다 (PA-05)       | 확정 |
| 짝       | 일치                | 모든 비교 컬럼·필드가 일치                                                                     | 확정 |

- Oracle에서는 빈 문자열이 NULL로 저장되므로 DB 컬럼에서 NULL과 빈 문자열을 구분하지 않는다.
- 비교는 DB에서 읽은 값을 문자열로 변환한 값 기준으로 한다. 값을 정규화(trim, 대소문자 통일 등)하지 않는다.
- BLOB·RAW 컬럼은 16진수 문자열로, LONG은 문자열로 변환해 같은 규칙으로 비교한다(PA-11, 기술 설계서 TD-09).

### 6.2 복호화·JSON 처리

| 항목          | 규칙                                                                                                           | 구분 |
| ------------- | -------------------------------------------------------------------------------------------------------------- | ---- |
| 복호화 방식   | SafeDB Java 라이브러리(`SimpleSafeDB`)로 복호화한다. 기본 정책은 KDKEY이고 컬럼별로 PANEN을 선택할 수 있다.        | 확정 |
| 복호화 대상   | 암호화 컬럼은 CLOB이다. 대상 테이블·컬럼은 사용자가 선택한다.                                                  | 확정 |
| JSON 펼치기   | 복호화 결과 JSON의 최상위 필드를 키별로 비교한다. 중첩 객체·배열은 없다고 알고 있으며, 있으면 해당 값을 JSON 문자열 그대로 비교한다(PA-09). | 확정/가정 |
| 필드 없음     | 한쪽에만 있는 키는 없는 쪽을 NULL로 보고 비교한다. 양쪽 모두 없으면 표시하지 않는다.                            | 확정 (PA-04) |
| 문자열 비교   | 고정 길이 전문은 없다. 가변 길이이므로 위치 단위 비교는 하지 않는다.                                           | 확정 |

### 6.3 처리 방식

1. 입력 짝에서 중복 없이 모은 거래번호A는 비교 키 기준으로 A쪽 환경 DB에서, 거래번호B는 B쪽 환경 DB에서 각각 묶음 조회한다(짝마다 쿼리를 날리지 않는다).
2. 조회 결과를 짝 순서대로 매칭해 컬럼 단위로 비교한다.
3. 복호화 대상 컬럼은 값이 있는 행만 복호화한 뒤 JSON 필드로 펼쳐 비교한다.
4. 결과를 요약과 상세로 화면에 반환한다.
5. 연결 실패·조회 타임아웃이 발생하거나 사용자가 중지하면 전체 비교를 종료하고 부분 결과는 만들지 않는다(PA-17, PA-18).

| PA-13 | 확정 | 양쪽 모두 NULL이면 일치, 공백·대소문자·숫자 형식 차이는 불일치                                                                     |
| PA-14 | 확정 | 환경(개발·테스트·운영) 간 SafeDB 인증 설정은 같다(사용자 확인). 실제 환경별 복호화는 구현 시 검증한다(R-05) |
| PA-15 | 확정 | 환경 간 비교 시 두 환경의 테이블·컬럼 구조는 완전히 동일하다. 별도의 구조 차이 처리는 하지 않는다 |
| PA-16 | 해결 | 환경 간 비교는 거래번호가 서로 달라 A·B를 직접 입력한다. 입력 단축 기능은 추가하지 않는다 |
| PA-17 | 확정 | 예외 처리 규칙: 거래번호 입력에 오류 줄이 있으면 비교를 시작하지 않고 수정을 요구한다. 최대 건수(1,000쌍) 초과 시 전체를 거절한다. DB 연결 실패·조회 타임아웃 시 전체 비교를 실패로 처리하고 부분 결과는 만들지 않는다 |
| PA-18 | 확정 | 비교 중지 시 지금까지의 부분 결과도 버리고 비교를 취소한다(PA-17의 "부분 결과 없음"과 일관). 중지 후 입력값 유지는 사용자 시나리오(SA-07)에서 확정했고, 취소 시 결과 폐기는 기술 설계서(TD-14)에서 설계했다 |
| PA-19 | 확정 | 비교 키 컬럼 타입은 문자형(CHAR, VARCHAR2, NCHAR, NVARCHAR2)과 NUMBER만 지원한다. 그 밖의 타입(DATE, RAW 등) 컬럼은 비교 키 후보에서 제외하며, 단일 PK의 타입이 이에 해당하면 기본값 없이 사용자가 다른 컬럼을 고른다(v1.4). NUMBER 비교 키에 숫자가 아닌 거래번호가 입력되면 입력 오류 줄로 처리한다 |
| PA-20 | 가정 | 인덱스가 없는 컬럼을 비교 키로 고르면 묶음 조회가 느릴 수 있다. 성능은 실제 환경에서 확인한다(실행 계획 INT-04 M-05). 현재 대상 테이블은 비교 키(control_no)가 PK의 첫 번째 컬럼이라 PK 인덱스를 사용한다 |
