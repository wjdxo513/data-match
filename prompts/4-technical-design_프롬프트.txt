## 1. 역할 및 목적

너는 10년 이상 경력의 Java/Spring Boot 소프트웨어 아키텍트이자 풀스택 개발 전문가야. 요구사항을 분석하고 실제 구현할 수 있는 시스템 아키텍처, 데이터 처리 구조, API 및 개발 원칙을 설계하는 역할을 수행해.

나는 사내 DB 거래 데이터 비교 자동화 프로그램인 **DataMatch**를 개발하고 있어. 현재 PRD, 사용자 시나리오, 화면 정의서 작성이 완료되었으며, 다음 단계로 기술 설계서를 작성하려고 해.

프로젝트 저장소의 기존 문서를 분석하고, 확정된 요구사항을 충족하면서도 구현과 유지보수가 쉬운 기술 설계서를 작성해 줘.

최종 산출물은 `docs/4-technical-design.md`야.

## 3. 기술 설계 기본 원칙

DataMatch는 사내 개발자와 운영 담당자가 사용하는 소규모 웹 애플리케이션이야. 복잡한 엔터프라이즈 아키텍처보다는 **단순하고 이해하기 쉬우며 유지보수가 편리한 구조**를 우선해 줘.

오버엔지니어링을 금지하고, 요구사항을 만족하는 최소한의 구조로 설계해 줘. 모놀리식 아키텍처를 우선 검토하고, 마이크로서비스, 메시지 큐, Redis, 별도 작업 서버 등은 명확한 필요성이 없는 한 도입하지 마.

Java/Spring Boot 기반 백엔드를 우선 검토해 줘. SafeDB가 Java 라이브러리인 점과 기존 사내 개발 환경을 고려하되, 실제 기술 스택과 버전은 호환성을 검토한 뒤 결정해 줘.

프론트엔드는 React 등의 기술을 검토하되, 별도 프레임워크 사용에 따른 복잡성과 장점을 비교해 줘. 프로젝트 규모가 작으므로 불필요한 전역 상태 관리 라이브러리는 사용하지 않는 방향을 우선해 줘.

기존 Oracle DB의 데이터를 조회하는 것이 목적이므로, 신규 데이터베이스나 테이블을 불필요하게 생성하지 마. 로그인, 사용자 관리, 비교 이력 저장, 비교 설정 저장 등 MVP에 없는 기능도 추가하지 마.

모든 기술 설계는 PRD의 FR/NFR, 사용자 시나리오의 SN, 화면 정의서의 SC와 연결할 수 있도록 작성해 줘.

## 4. 핵심 기술 설계 요구사항

### 4.1 시스템 아키텍처

DataMatch는 담당자 PC에서 로컬 실행하는 웹 애플리케이션이며, 브라우저를 통해 사용한다. 개발·테스트·운영 Oracle DB와 SafeDB 서버에 접근할 수 있는 환경을 전제로 한다.

백엔드, 프론트엔드, Oracle DB, SafeDB 라이브러리 간 구성과 통신 흐름을 설계해 줘. 프로젝트 규모를 고려하여 배포와 실행이 간단한 구조를 우선해 줘.

프론트엔드와 백엔드를 분리해서 개발하더라도 실행 및 배포 과정이 지나치게 복잡해지지 않도록 검토해 줘.

### 4.2 DB 연결 및 환경 선택

사용자는 A쪽과 B쪽 환경을 각각 개발·테스트·운영 중에서 선택할 수 있어야 해. 동일한 환경을 선택할 수도 있고 서로 다른 환경을 선택할 수도 있어.

DB 연결 정보는 환경별 설정 파일로 관리하며, 화면에서는 비밀번호를 입력하지 않아. 테이블과 컬럼 메타데이터는 A쪽 환경을 기준으로 조회하고, A·B 환경의 테이블 구조는 동일하다는 확정된 전제를 적용해 줘.

Oracle DB에 대한 읽기 전용 접근을 보장하고, DB 연결 관리, 연결 재사용, 쿼리 타임아웃, 환경 전환 시 처리 방식을 설계해 줘.

### 4.3 테이블 검색 및 컬럼 선택

사용자는 접속 계정이 조회할 수 있는 스키마의 테이블을 검색할 수 있어야 해. 테이블은 `스키마.테이블` 형태로 표시하며, 단일 PK가 존재하는 테이블만 비교 대상으로 선택할 수 있어.

테이블 선택 후 컬럼명과 데이터 타입을 조회하고 PK 컬럼을 자동으로 인식해야 해. PK 컬럼도 비교 컬럼으로 선택할 수 있으며, 비교 대상 컬럼은 사용자가 체크박스로 선택해.

대규모 Oracle 스키마에서도 검색 성능을 유지할 수 있도록 서버 측 검색, 자동완성 후보 수 제한, 입력 지연(Debounce) 등을 검토해 줘. 전체 메타데이터를 매 요청마다 조회하는 비효율적인 구조는 피하도록 설계해 줘.

테이블 및 컬럼명은 반드시 조회된 메타데이터를 기준으로 검증하고, 거래번호 등 사용자 입력값은 SQL 바인딩을 적용해 줘.

### 4.4 거래번호 다건 비교

거래번호는 한 줄에 `거래번호A,거래번호B` 형식으로 입력하며, 쉼표 또는 탭을 구분자로 사용해. 빈 줄은 무시하고 값의 앞뒤 공백은 제거하며, 형식 오류가 있으면 해당 줄 번호와 사유를 표시해야 해.

한 번에 최대 1,000쌍까지 입력할 수 있어야 해. 거래번호A는 A쪽 DB에서, 거래번호B는 B쪽 DB에서 조회하고, 입력 순서를 유지한 상태로 비교 결과를 반환해야 해.

거래번호를 짝마다 개별 조회하지 않고 PK 기반 묶음 조회를 활용해 줘. Oracle IN 조건의 제약, 중복 거래번호 처리, 쿼리 타임아웃, 메모리 사용량 등을 고려하여 효율적인 조회 및 매칭 구조를 설계해 줘.

비교는 문자열 변환 후 정확히 같은지를 기준으로 하며, 별도 정규화나 대소문자 통일은 수행하지 않아. 데이터 타입별 변환과 NULL 처리에 대해서는 PRD의 확정 규칙을 그대로 적용해 줘.

### 4.5 SafeDB 복호화 및 JSON 비교

사용자가 선택한 CLOB 컬럼을 SafeDB 복호화 대상으로 지정할 수 있어야 해. 복호화 정책은 KDKEY가 기본이며 PANEN도 선택할 수 있어.

SafeDB Java 라이브러리인 `SimpleSafeDB`를 사용하는 구조를 검토해 줘. 기존 사내 프로젝트에서 사용하는 라이브러리나 설정을 참고할 수 있다면 재사용 가능성을 먼저 확인해 줘.

복호화 결과는 JSON 최상위 필드를 기준으로 비교해. 한쪽에만 존재하는 필드는 없는 쪽을 NULL로 처리하며, 중첩 객체와 배열은 PRD의 규칙에 따라 처리해 줘.

복호화 실패 또는 JSON 파싱 실패는 해당 컬럼의 오류로 처리하고, 나머지 컬럼과 거래 쌍은 계속 비교해야 해. 복호화된 평문은 로그에 기록하거나 불필요하게 파일에 저장하지 않도록 설계해 줘.

개발·테스트·운영 환경 간 SafeDB 복호화가 실제로 가능한지 검증하는 방법도 포함해 줘.

### 4.6 비교 진행률 및 중지 처리

화면 정의서의 SC-02는 비교 진행 상태를 표시하는 모달이야. 비교 실행 중 처리 완료 건수, 전체 건수, 진행률을 표시하고 사용자가 비교를 중지할 수 있어야 해.

Oracle 조회, SafeDB 복호화, JSON 파싱, 비교 처리 등의 과정을 고려하여 실제 진행 상황을 전달할 수 있는 구조를 설계해 줘.

Polling, SSE 등 가능한 방식을 비교하되, 로컬에서 실행하는 소규모 프로그램에 적합한 가장 단순한 방식을 추천해 줘.

필요하다면 작업 ID 기반 비동기 처리 구조를 검토하되, 불필요한 외부 인프라는 도입하지 마.

진행률 계산 기준, 작업 취소 요청, 실행 중인 작업 정리, 중지 시 입력값 유지, 결과 폐기, 작업 완료 후 메모리 정리 방식을 정의해 줘.

**진행률은 실제 처리 상태와 일치해야 하며, 단순히 시간이 지남에 따라 증가하는 가짜 진행률을 사용하지 마.**

작업 중 DB 연결 실패 또는 조회 타임아웃이 발생하면 PRD와 사용자 시나리오의 규칙에 따라 전체 비교를 실패로 처리해야 해.

### 4.7 비교 결과 및 화면 상태

DataMatch는 페이지 이동 없는 단일 페이지 웹 구조야. SC-01은 비교 설정, SC-02는 진행 모달, SC-03은 비교 결과 영역으로 구성되어 있어.

프론트엔드에서는 환경 선택, 테이블·컬럼 선택, SafeDB 복호화 설정, 거래번호 입력, 비교 진행 상태, 비교 결과를 관리해야 해.

비교가 완료되면 거래 쌍별 일치·불일치·누락 요약 목록을 표시하고, 사용자가 특정 짝을 선택하면 컬럼 및 JSON 필드별 상세 결과를 보여줘.

비교 결과에는 실제 비교를 수행한 당시의 환경, 테이블, 컬럼 정보가 포함되어야 해. 사용자가 현재 입력값을 변경하더라도 기존 결과에 표시된 비교 조건이 바뀌지 않도록 설계해 줘.

새 비교 실행 시 기존 결과 처리, 입력 오류나 비교 중지 시 입력값 유지, 브라우저 새로고침 시 상태 초기화 등은 화면 정의서의 확정 규칙을 적용해 줘.

긴 데이터는 화면에서 접고 펼칠 수 있어야 하며, JSON 필드는 `컬럼명.필드명` 형태로 표시하도록 데이터 구조를 설계해 줘.

### 4.8 엑셀 다운로드

비교 결과를 Excel 파일로 다운로드할 수 있어야 해. 요약과 상세 결과를 포함하고, A·B 환경 정보 및 불일치 항목의 강조 표시를 유지해야 해.

Apache POI 등 적합한 Java 라이브러리를 검토하고, 파일 생성 방식과 메모리 사용량을 고려해 줘.

별도 DB 저장이나 영구 파일 보관 없이 구현할 수 있는 방법을 우선 검토해 줘. 엑셀 생성 실패 시 화면의 비교 결과가 유지되고 재시도할 수 있어야 해.

파일명과 시트 구성은 기술 설계 단계에서 결정해 줘.

### 4.9 오류 처리 및 보안

입력값 오류, DB 연결 실패, 테이블 조회 실패, PK 미지원, 거래 누락, SafeDB 복호화 실패, JSON 파싱 실패, 타임아웃, 비교 중지, 엑셀 생성 실패를 구분해서 설계해 줘.

전체 작업 실패와 개별 거래·컬럼 오류를 구분하고, PRD의 확정된 판정 규칙을 변경하지 마.

운영 DB는 읽기 전용 계정을 사용하고 SELECT 외의 데이터 변경 SQL을 실행하지 않도록 해 줘. 접속 정보, 인증서, SafeDB 인증 설정은 Git에서 제외하고, 복호화 평문과 민감한 거래 정보를 로그에 남기지 않도록 설계해 줘.

로그인과 사용자별 권한 구분은 MVP에 포함하지 않으므로 임의로 도입하지 마. 다만 로컬 웹 서버의 외부 접근 차단 등 현재 실행 구조에 필요한 기본 보안 조치는 검토해 줘.

### 시스템 아키텍처 표현

전체 구성은 Mermaid 다이어그램으로 작성해 줘. 주요 데이터 비교 흐름과 비동기 작업 처리는 필요할 경우 시퀀스 다이어그램으로 표현해 줘.

다이어그램은 실제 구현 구조를 설명하는 데 필요한 수준으로만 작성하고, 불필요하게 세분화하지 마.

### API 설계 수준

각 API는 HTTP Method, URL, 목적, 요청값, 응답값, 오류 상황을 표로 정리해 줘.

핵심 API의 JSON 요청·응답 예시는 필요한 경우에만 작성하고, 상세 OpenAPI 명세를 중복 작성하지 마. 별도 API 명세가 필요하면 기술 설계서와 일치하는 `swagger.yaml` 파일을 생성하는 방식을 제안해 줘.

### 데이터 설계 수준

기존 Oracle 거래 DB는 조회 대상으로 사용하며, 비교 설정이나 실행 이력을 저장하기 위한 신규 테이블은 기본적으로 만들지 마.

메모리 기반 작업 상태와 결과 관리 방식을 우선 검토하고, 별도 DB나 캐시가 필요한 경우에는 그 이유와 대안을 설명해 줘.

신규 테이블이 필요하지 않다면 ERD와 `schema.sql`은 작성하지 않아도 돼.

## 6. 기술 설계 단계에서 결정할 사항

화면 정의서의 WA-07에 남아 있는 사항을 반드시 검토해 줘.

| 항목 | 검토 내용 |
|---|---|
| 진행률 갱신 | Polling, SSE 등 처리 상태 전달 방식 |
| 비교 중지 | 실제 서버 작업 취소 및 정리 방법 |
| 테이블 자동완성 | 입력 지연 시간, 후보 반환 건수, 검색 범위 |
| 엑셀 파일명 | 파일명 규칙 및 날짜·시간 포함 여부 |
| 엑셀 시트 | 요약 및 상세 시트 구성 |
| 누락 상태 색상 | 불일치와 구분되는 표시 방식 |

그 밖에도 기술 설계를 위해 반드시 결정해야 하는 사항이 있다면 제안해 줘.

각 항목에 대해 권장 방안, 선정 이유, 구현 난이도, 주의사항을 간결하게 설명하고 사용자의 승인을 받은 뒤 확정해 줘.

## 7. 작업 진행 방식

다음 순서로 진행해 줘.

1. `.claude/CLAUDE.md`와 기존 설계 문서를 읽고 확정 요구사항 및 미결 사항을 분석한다.
2. 현재 프로젝트의 파일 구조와 재사용 가능한 코드 및 라이브러리가 있는지 확인한다.
3. 기술 설계에서 반드시 결정해야 하는 항목을 정리한다.
4. 권장 기술 스택과 시스템 아키텍처를 먼저 제안한다.
5. 주요 설계 대안을 구현 난이도와 유지보수 관점에서 비교한다.
6. 내가 설계 방향을 검토하고 승인하면 `docs/4-technical-design.md`를 작성한다.
7. 최종 작성 후 PRD, 사용자 시나리오, 화면 정의서와의 정합성을 검증한다.
8. 필요한 경우 `.claude/CLAUDE.md`의 문서 목록과 상태를 갱신한다.

이미 확정된 사항은 다시 질문하지 말고, 실제 기술 설계에 영향을 주는 미결 사항만 질문해 줘.

**지금은 기술 설계서 전체를 바로 작성하지 말고, 권장 기술 스택과 아키텍처, 핵심 기술적 결정 사항을 먼저 제안해 줘.**

## 8. 문서 작성 규칙

문서는 Markdown 형식으로 작성하고 제목 바로 아래에 버전 이력과 변경 이력을 포함해 줘. 변경 사항은 버전별로 기록하며, 확정된 상위 문서의 파일명과 버전을 머리말에 명시해 줘.

불필요한 개행을 최소화하고 관련 문장은 하나의 문단으로 작성해 줘. 문장마다 줄을 바꾸거나 짧은 항목을 지나치게 나열하지 말고, 제목과 문단 중심으로 구성해 줘.

확정된 요구사항과 사용자 시나리오는 중복 정의하지 않고 기존 ID를 참조해 줘. 기술 설계 과정에서 새로 결정한 사항은 별도의 설계 결정 ID로 관리하고, 미결 사항은 문서 마지막에 정리해 줘.

문서 간 내용이 충돌하면 임의로 수정하거나 재해석하지 마. 충돌 내용을 명시하고 해결 방안을 제안해 줘.

기술 스택과 라이브러리는 프로젝트 요구사항에 필요한 최소한으로 선택하며, 향후 확장 가능성만을 이유로 불필요한 기술을 도입하지 마.

모든 MVP 요구사항(FR-01~FR-09)이 기술 설계에 반영되었는지 확인하고, 이후 Task 단위 개발 계획을 작성할 수 있을 정도로 구체적으로 작성해 줘.

최종 문서 저장 경로는 **`docs/4-technical-design.md`**이며, 문서 작성과 검토가 끝나면 다음 단계인 실행 계획 작성으로 진행할 수 있도록 해 줘.
