1. 역할 및 목적

너는 10년 이상 경력의 IT 서비스 기획자이자 UI/UX 설계 전문가야. 나는 사내 DB 거래 데이터 비교 자동화 프로그램인 DataMatch를 개발하고 있어.

현재 PRD와 사용자 시나리오 문서 작성이 완료되었으며, 다음 단계로 화면 정의서(Screen Specification)를 작성하려고 해. 첨부한 1-PRD.md와 2-user-scenario.md를 기준으로 실제 개발에 활용할 수 있는 화면 정의서를 작성해 줘.

두 문서를 최우선 기준으로 삼고, 문서 간 충돌하거나 정의되지 않은 사항은 임의로 결정하지 말고 별도로 정리해 줘.

2. 화면 설계 목표

DataMatch는 개발자와 운영 담당자가 사용하는 사내 웹 프로그램이야. 복잡한 디자인보다는 빠른 데이터 입력, 직관적인 비교 설정, 명확한 차이점 확인에 집중해 줘.

사용자가 최소한의 클릭으로 거래 비교를 실행할 수 있어야 하며, 환경·테이블·컬럼·거래번호를 한눈에 확인할 수 있도록 구성해 줘. 여러 거래번호를 복사해 한 번에 붙여넣기 편해야 하고, 비교 결과에서는 어떤 컬럼이나 JSON 필드가 다른지 쉽게 확인할 수 있어야 해.

운영 DB를 선택한 경우에는 해당 환경을 명확하게 표시하고, 데스크톱 웹 환경을 우선으로 설계해 줘. 불필요한 팝업이나 페이지 이동은 최소화해 줘.

3. 화면 구성

SC-01. 거래 비교 설정

A쪽과 B쪽 환경(개발/테스트/운영)을 각각 선택하고, 비교할 테이블을 검색하는 화면이야. 테이블은 스키마.테이블 형식으로 표시하며, 단일 PK를 자동으로 인식해야 해.

테이블 선택 후 컬럼명과 타입을 확인하고 비교할 컬럼을 체크박스로 선택할 수 있어야 해. CLOB 컬럼은 SafeDB 복호화 대상으로 지정하고, 복호화 정책(KDKEY/PANEN)을 선택할 수 있도록 구성해 줘.

거래번호는 거래번호A,거래번호B 형식으로 여러 줄을 입력할 수 있어야 하며, 입력 건수 표시, 형식 검증, 비교 실행 기능을 포함해 줘.

SC-02. 비교 진행 상태

비교 실행 후 전체 거래 쌍 수와 처리 완료 건수를 표시하고, 진행률 및 비교 중지 기능을 제공해 줘. 비교가 완료되면 결과 화면으로 이동하고, 연결 실패나 타임아웃이 발생하면 오류 내용을 안내해야 해.

별도의 페이지보다는 SC-01 내부의 진행 영역 또는 모달로 구현하는 방식을 우선 검토해 줘. 진행률 및 중지 기능은 사용자 시나리오에 정의된 내용을 반영하되, 실제 처리 방식은 상세 설계 단계에서 결정하도록 해 줘.

SC-03. 비교 결과

비교 완료 후 거래 쌍별 일치·불일치·누락 결과를 요약해서 보여주는 화면이야. 사용자가 특정 거래 쌍을 선택하면 컬럼별 A값과 B값을 나란히 확인할 수 있어야 해.

SafeDB 복호화 컬럼은 JSON 필드 단위로 비교 결과를 표시하고, 불일치 및 복호화 오류 항목을 강조해 줘. A쪽과 B쪽의 DB 환경을 명확하게 구분하고, 비교 결과를 엑셀로 다운로드할 수 있어야 해.

불일치만 보기 필터, 비교 설정 저장, 엑셀 업로드 등 MVP에서 제외된 기능은 포함하지 마.

4. 화면 정의서 작성 형식

최종 문서는 3-screen-specification.md라는 이름의 Markdown 문서로 작성해 줘.

4.1 화면 목록

화면 ID, 화면명, 화면 유형, 주요 기능, 관련 사용자 시나리오를 표로 정리해 줘.

4.2 화면별 상세 정의

각 화면은 다음 항목으로 구성해 줘.

화면 개요: 화면 목적, 접근 경로, 사전 조건, 관련 PRD 요구사항 및 사용자 시나리오를 작성해 줘.

화면 레이아웃: 주요 UI 영역과 배치를 ASCII 와이어프레임으로 표현해 줘. 실제 화면 구조를 이해할 수 있도록 구성하되 지나치게 복잡하게 작성하지 마.

UI 구성 요소: 요소 ID, 요소명, UI 유형, 초기값, 필수 여부, 동작 및 설명을 표로 정리해 줘.

사용자 인터랙션: 버튼 클릭, 선택값 변경, 데이터 입력 등에 따른 시스템 동작을 정의해 줘. 사용자 행동과 시스템 반응을 구분해서 작성해 줘.

입력값 검증 및 오류 처리: 입력 오류, DB 연결 실패, 조회 결과 없음, 거래 누락, 복호화 실패 등 주요 예외 상황의 처리 방식과 사용자 안내 메시지를 정리해 줘. 오류 메시지는 실제 화면에 사용할 수 있는 자연스러운 한국어로 작성해 줘.

화면 상태: 초기 상태, 로딩 중, 정상 입력, 입력 오류, 비교 실행 중, 비교 완료, 비교 실패 등 필요한 화면 상태를 정의해 줘.

4.3 화면 전환 흐름

사용자가 비교 환경을 선택하고 거래번호를 입력한 뒤 비교 결과를 확인하기까지의 전체 흐름을 Mermaid 다이어그램으로 작성해 줘. 각 화면의 이동 조건과 오류 발생 시 복귀 흐름도 함께 설명해 줘.

4.4 공통 UI/UX 정책

버튼 활성화 및 비활성화 조건, 로딩 표시, 오류 메시지, 운영 환경 경고, 일치·불일치·누락 상태 표현, 입력값 유지 정책, 긴 데이터 및 JSON 표시 방식, 엑셀 다운로드 동작을 정의해 줘.

4.5 요구사항 추적표

화면 ID와 PRD 요구사항(FR-01~FR-09), 사용자 시나리오(SN-xx)를 연결하는 표를 작성해 줘. MVP 기능 중 화면 설계에서 누락된 항목이 없는지 확인해 줘.

4.6 추가 확인 사항

PRD와 사용자 시나리오에 정의되지 않은 화면 동작이나 정책을 정리해 줘. 특히 사용자 시나리오의 SA-01~SA-08을 확인하고, 확정이 필요한 항목은 별도로 표시해 줘.

5. 작업 진행 방식

먼저 첨부한 PRD와 사용자 시나리오를 분석하고, 문서 간 충돌 사항과 미결정 사항을 파악해 줘. 이후 권장 화면 목록과 전체 화면 흐름을 제안하고, 화면 구성을 개선할 수 있는 부분이 있다면 근거와 함께 설명해 줘.

내가 화면 구성을 검토하고 승인하면 상세 화면 정의서를 작성해 줘. 문서 완성 후에는 PRD의 모든 MVP 요구사항과 사용자 시나리오가 반영되었는지 검증해 줘.

6. 작성 원칙 및 주의사항

PRD와 사용자 시나리오에 없는 기능을 임의로 추가하지 마. 확정된 요구사항과 제안 사항을 명확하게 구분하고, 미결정 사항은 사용자에게 질문하거나 별도 항목으로 관리해 줘.

화면 정의서는 실제 개발에 활용할 수 있도록 구체적으로 작성하되, 구현 코드와 API 명세 및 DB 상세 설계는 포함하지 마. 동일한 설명을 반복하지 않고 간결하게 작성해 줘.

문서 가독성을 위해 불필요한 줄바꿈을 최소화하고, 관련된 문장은 하나의 문단으로 작성해 줘. 제목과 소제목을 기준으로 문단을 구분하고, 표가 적절한 부분에만 표를 사용해 줘. 문장마다 줄을 바꾸거나 짧은 항목을 지나치게 나열하지 마.

문서 상단에는 기존 PRD 및 사용자 시나리오와 동일한 형식의 버전 이력과 변경 이력을 포함해 줘.

7. 첫 번째 요청

지금은 전체 화면 정의서를 바로 작성하지 말고, PRD와 사용자 시나리오를 분석한 뒤 권장 화면 구성과 화면 전환 흐름부터 제안해 줘. 추가로 확정해야 할 사항이 있다면 중요한 질문만 간결하게 정리해 줘.
