# DataMatch 개발 실행 계획서 작성 프롬프트

## 1. 역할 및 목적

너는 10년 이상 경력의 소프트웨어 아키텍트이자 테크 리드이며, AI 에이전틱 개발을 위한 Task 분해와 개발 실행 계획 수립 전문가야.

나는 사내 DB 거래 데이터 비교 자동화 프로그램인 **DataMatch**를 개발하고 있어. 현재 PRD, 사용자 시나리오, 화면 정의서, 기술 설계서를 작성했으며, 이제 AI 에이전트가 문서를 기준으로 실제 개발할 수 있도록 실행 계획을 수립하려고 해.

프로젝트 저장소의 기존 문서와 소스 코드를 분석하고, 전체 MVP 개발 범위를 독립적으로 실행 가능한 Task로 분해해 줘. 각 Task는 Claude Code의 서브에이전트와 개발 스킬이 수행할 수 있어야 하며, 구현 완료 여부를 테스트로 판단할 수 있도록 작성해 줘.

최종 산출물은 `docs/5-plan.md`야.

## 3. 실행 계획 수립 원칙

DataMatch는 소규모 사내 웹 프로그램이므로 오버엔지니어링을 금지하고, MVP 구현에 필요한 작업만 계획해 줘.

Task는 AI가 한 번의 개발 스킬 실행으로 처리할 수 있는 크기로 분리해 줘. 너무 큰 Task는 나누고, 지나치게 작은 Task는 합쳐 줘. 클래스나 파일 하나를 만드는 작업마다 무조건 Task를 생성하지 마.

각 Task는 명확한 입력 문서, 구현 범위, 선행 Task, 테스트 방법 및 완료 조건을 가져야 해.

구현 순서는 프로젝트 초기 설정, 핵심 백엔드 기능, 프론트엔드 기능, 통합 테스트를 기본으로 하되, 독립적인 작업은 병렬 개발이 가능하도록 의존성을 명확하게 정의해 줘.

**기술 설계서에서 이미 결정한 기술 스택과 아키텍처를 다시 설계하지 말고, 확정된 설계를 실제 코드로 구현하는 작업으로 분해하는 데 집중해 줘.**

## 4. Task 분류

개발 Task는 다음 유형으로 분류해 줘.

| 유형 | 의미 | 예시 |
|---|---|---|
| SETUP | 프로젝트 초기 설정 및 실행 환경 | Spring Boot, React, Gradle, Vite, 빌드·배포 |
| DB | Oracle DB 연결 및 데이터 접근 | 환경별 DataSource, 메타데이터, 거래 조회 |
| BE | 백엔드 비즈니스 로직 및 API | 거래 비교, SafeDB, JobManager, Excel |
| FE | 프론트엔드 화면 및 상태 관리 | 비교 설정, 진행 모달, 결과 화면 |
| INT | 통합 및 E2E 테스트 | 실제 연동 검증, 성능, 배포 검증 |

각 Task의 ID는 `SETUP-01`, `DB-01`, `BE-01`, `FE-01`, `INT-01`과 같이 부여해 줘.

별도의 PRE Task는 꼭 필요한 사전 작업이 있을 때만 추가하고, 단순한 설정이나 문서 작업은 해당 SETUP Task에 포함해 줘.

## 5. 개발 범위

### 5.1 프로젝트 초기 설정

기술 설계서의 TD-01~TD-04, TD-18, TD-21을 기준으로 개발 환경과 실행 구조를 구성해 줘.

JDK 11, Spring Boot 2.7.18, Gradle 8.9, React 18, Vite, TypeScript를 사용하며, 백엔드와 프론트엔드 프로젝트 초기 설정, 의존성 관리, Git 제외 규칙, 기본 테스트 환경을 포함해 줘.

프론트엔드 빌드 결과를 Spring Boot 정적 리소스로 포함하고, `datamatch.jar`, `lib/`, `config/`, `start.bat`을 포함하는 배포 zip 생성 작업도 계획에 반영해 줘.

SafeDB jar 9개와 인증 설정 파일의 관리 방식은 기술 설계서를 따라야 하며, 민감한 설정 파일이 Git이나 배포 zip에 포함되지 않도록 검증하는 Task를 포함해 줘.

### 5.2 Oracle DB 접근

개발·테스트·운영 환경별 DataSource를 구성하고 JDBC/JdbcTemplate 기반으로 DB에 연결하는 작업을 계획해 줘.

읽기 전용 계정을 사용하고 SELECT 전용 SQL 생성, 메타데이터 기반 식별자 검증, 바인드 변수, 조회 타임아웃을 구현하도록 해 줘.

테이블 자동완성 검색, 단일 PK 판별, 컬럼 및 데이터 타입 조회, 거래번호 묶음 조회를 포함해 줘.

대규모 스키마 검색 시 후보 최대 30건과 서버 측 조회 방식을 적용하고, Oracle 버전 및 JDBC 드라이버 호환성 검증도 반영해 줘.

### 5.3 거래 비교 엔진

거래번호 A·B 쌍 입력을 파싱하고 형식 오류, 빈 값, 최대 1,000쌍 초과, 숫자형 PK 입력 오류를 검증하는 기능을 계획해 줘.

입력된 거래번호는 100쌍 단위 청크로 묶어 A·B 환경에서 각각 조회하고, 입력 순서대로 매칭하도록 해 줘.

컬럼별 문자열 변환과 NULL 처리, 일치·불일치·누락 판정, 오류 발생 시 전체 실패 또는 개별 컬럼 오류 분류를 구현해 줘.

핵심 비교 로직은 실제 Oracle DB 없이도 단위 테스트할 수 있도록 구성해 줘.

### 5.4 SafeDB 복호화 및 JSON 비교

기술 설계서의 `SafeDbDecryptor` 구조를 기준으로 KDKEY/PANEN 복호화 기능을 구현하는 Task를 포함해 줘.

복호화 대상 CLOB 컬럼 선택, SafeDB 라이브러리 연동, 문자셋 처리, JSON 최상위 필드 비교, 복호화 오류 및 JSON 파싱 오류 처리를 포함해 줘.

SafeDB 라이브러리와 인증 설정은 기존 사내 프로젝트의 사용 방식을 참조하되, 실제 동작 여부를 검증하는 작업을 별도로 관리해 줘.

SafeDB 서버 연결이나 복호화가 불가능한 환경에서도 비교 엔진의 단위 테스트를 수행할 수 있도록 가짜 복호화 구현을 사용해 줘.

### 5.5 비동기 비교 작업 관리

기술 설계서의 인메모리 JobManager 구조를 기준으로 Task를 구성해 줘.

동시 비교 작업은 1개만 허용하고, 서버에는 마지막 작업 결과만 유지하도록 해 줘.

비교 시작 API, 작업 상태 조회, 진행률 Polling, 중지 요청, 취소 상태 처리, 전체 실패 및 결과 폐기를 구현해야 해.

진행률은 실제 완료된 거래 쌍 수를 기준으로 계산하고, 프론트엔드는 1초 간격으로 상태를 조회하도록 해 줘.

중지는 취소 플래그와 JDBC `Statement.cancel()`을 사용하며, SafeDB 복호화 호출 도중 즉시 중단되지 않을 수 있다는 기술 설계서의 제한도 반영해 줘.

### 5.6 결과 조회 및 Excel 다운로드

거래 쌍별 요약 결과와 컬럼·JSON 필드별 상세 결과를 조회하는 API를 구현하도록 해 줘.

요약에는 비교 조건, 전체 건수, 일치·불일치·누락 건수와 거래 쌍별 판정을 포함하고, 상세에는 A값·B값·상태·오류 사유를 포함해야 해.

Excel은 Apache POI XSSF로 생성하고, '요약'과 '상세' 시트를 포함하도록 해 줘. 불일치 항목은 빨간색, 누락 항목은 별도 색상으로 표현하고, 비교 당시의 환경 정보를 함께 기록해야 해.

엑셀 생성 오류가 발생해도 화면의 비교 결과가 유지되도록 해 줘.

### 5.7 프론트엔드

React 18, Vite, TypeScript 기반의 단일 페이지 UI를 구현하는 Task를 계획해 줘.

화면 정의서의 SC-01~SC-03을 기준으로 다음 기능을 구현해야 해.

- SC-01: 환경 선택, 테이블 검색, 컬럼 선택, SafeDB 지정, 거래번호 입력 및 검증
- SC-02: 진행률 표시, 상태 Polling, 비교 중지, 실패 안내
- SC-03: 결과 요약 목록, 상세 비교, 긴 값 펼치기, Excel 다운로드

프론트엔드 상태는 `useReducer`와 `useState`를 우선 활용하고, 별도의 전역 상태 관리 라이브러리나 UI 프레임워크를 도입하지 마.

입력값 검증 규칙은 백엔드와 동일한 테스트 케이스를 사용하여 불일치가 발생하지 않도록 해 줘.

UI 디자인은 기존 프로토타입과 화면 정의서를 기준으로 하며, 확정되지 않은 기능을 추가하지 마.

### 5.8 보안 및 품질

서버의 `127.0.0.1` 바인딩, Host·Origin 검증, JSON 요청 제한 등 기술 설계서의 로컬 보안 정책을 반영해 줘.

DB 접속 정보, SafeDB 인증 설정, 거래번호, 복호화 평문 등이 로그나 Git 저장소에 포함되지 않도록 검증해 줘.

각 Task에서는 구현 기능에 필요한 단위 테스트와 예외 테스트를 수행하며, 핵심 로직의 테스트를 최종 통합 단계까지 미루지 마.

## 6. Task 작성 형식

먼저 전체 Task 목록을 표로 작성해 줘.

| Task ID | Task명 | 주요 작업 | 선행 Task | 관련 요구사항 | 담당 스킬 |
|---|---|---|---|---|---|

각 Task의 상세 내용은 다음 형식으로 작성해 줘.

### BE-01. 거래번호 입력 파서 구현

**목적:** 거래번호 A·B 쌍의 입력 규칙을 검증하고 비교 가능한 데이터 구조로 변환한다.

**참조 문서:** PRD FR-05, 사용자 시나리오 SN-E03, 화면 정의서 SC-01, 기술 설계서 TD-08.

**선행 Task:** SETUP-01

**구현 범위:** 거래번호 입력 문자열 파싱, 쉼표·탭 구분, 빈 줄 처리, 공백 제거, 구분자 오류, 최대 입력 건수 검증, 숫자형 PK 검증을 포함한다.

**완료 조건:**
- [ ] 정상적인 거래번호 쌍을 입력 순서대로 파싱한다.
- [ ] 잘못된 형식은 오류 코드와 줄 번호를 반환한다.
- [ ] 최대 1,000쌍을 초과하면 비교를 시작하지 않는다.
- [ ] 숫자형 PK에 유효하지 않은 값이 있으면 오류를 반환한다.
- [ ] 정상·예외·경계값 단위 테스트가 통과한다.

**검증 방법:** JUnit 단위 테스트 실행 및 결과 확인.

**담당 스킬:** `/develop-backend`

위 내용은 형식 예시이며, 실제 Task ID와 작업 분리는 전체 의존성을 분석해 결정해 줘.

각 Task에는 다음 정보가 빠짐없이 포함되어야 해.

1. Task ID 및 작업명
2. 작업 목적
3. 관련 요구사항 및 설계 ID
4. 선행 Task
5. 구현 범위
6. 체크박스 형태의 완료 조건
7. 테스트 및 검증 방법
8. 담당 스킬 또는 에이전트

완료 조건은 "정상 동작한다", "적절히 처리한다" 같은 추상적인 표현을 피하고, 테스트로 판단 가능한 구체적인 문장으로 작성해 줘.

## 7. Task 의존성 및 실행 순서

Task 간 선행 관계를 분석하고, 어떤 작업을 먼저 수행해야 하는지 명확하게 작성해 줘.

백엔드와 프론트엔드가 독립적으로 진행할 수 있는 부분은 병렬 개발이 가능하도록 구성해 줘. 단, 동일 파일을 동시에 수정하거나 API 계약이 확정되지 않은 상태에서 충돌이 발생하지 않도록 해 줘.

전체 Task를 개발 단계별로 묶고 Mermaid 의존성 다이어그램을 작성해 줘.

작업 순서는 실제 의존성을 기준으로 결정하되, 가능하면 핵심 기능 하나를 백엔드부터 프론트엔드까지 연결해 조기에 검증할 수 있도록 계획해 줘.

작업을 불필요하게 세분화하지 말고, AI가 관리하기 적절한 수의 Task로 구성해 줘.

## 8. 개발 착수 전 검증 및 미결 사항

기술 설계서 12장의 `TA-xx` 항목을 반드시 확인해 줘.

특히 다음 사항은 개발 계획에 반영해야 해.

| 항목 | 검증 내용 | 처리 방향 |
|---|---|---|
| TA-01 | SafeDB 설정 파일 탐색 경로 | 초기 SETUP 단계에서 검증 |
| TA-02 | SafeDB jar 및 환경별 복호화 | 연동 검증 Task |
| TA-03 | Oracle 버전과 JDBC 호환성 | DB 연동 초기 검증 |
| TA-07 | KDKEY/PANEN 문자셋 | 복호화 테스트에 포함 |
| TA-09 | 힙 메모리와 청크 처리 초기값 | 성능 테스트에서 확인 |
| TA-10 | 50쌍·500쌍 처리 성능 | 통합 성능 테스트 |
| TA-11 | SafeDB 스레드 안전성 | 순차 처리 유지, 병렬화 필요 시 별도 검증 |
| TA-13 | 시스템 스키마 검색 결과 | 기존 요구사항 유지, 필요 시 변경 제안 |

모든 미결 사항을 개발 착수의 차단 조건으로 만들지는 마. 실제로 선행 검증이 필요한 사항과 구현 또는 테스트 과정에서 확인할 수 있는 사항을 구분해 줘.

개발 전에 반드시 결정해야 하는 항목만 `D-xx`로 관리해 줘.

기술 설계서의 미결 사항을 임의로 해결된 상태로 변경하지 마.

## 9. 테스트 및 통합 검증 계획

개발 Task에는 해당 기능의 단위 테스트를 포함하고, 마지막 INT Task에서는 실제 사용자 시나리오 기반 통합 테스트를 수행하도록 계획해 줘.

통합 테스트는 다음 항목을 포함해 줘.

- 정상적인 동일 환경·서로 다른 환경 거래 비교
- 거래번호 형식 오류 및 최대 건수 초과
- 컬럼 및 PK 지원 여부 검증
- SafeDB 복호화 및 JSON 필드 비교
- 거래 데이터 누락 및 복호화 실패
- 비교 진행률 표시와 중지 처리
- DB 연결 실패와 쿼리 타임아웃
- 결과 요약·상세 표시 및 엑셀 다운로드
- 실제 배포 zip 생성과 `start.bat` 실행
- 읽기 전용 DB 접근 및 민감정보 로그 노출 여부

E2E 테스트는 Playwright를 활용하고, 테스트 결과는 `test/e2e/report.md`에 기록하도록 해 줘.

실제 개발·테스트·운영 DB와 SafeDB 서버를 이용해야 하는 검증은 자동 테스트와 구분하여 별도의 수동 검증 체크리스트로 관리해 줘. 실제 거래 데이터나 복호화 평문을 테스트 산출물에 기록하지 마.

테스트 환경이 없어 실행할 수 없는 항목은 성공으로 간주하지 말고 미검증 상태로 표시해 줘.

## 11. Task 실행 및 완료 관리 규칙

Task를 수행할 때는 해당 Task에 명시된 참조 문서와 선행 Task를 먼저 확인해야 해.

개발 스킬은 다음과 같은 방식으로 실행할 예정이야.

```text
/develop-backend BE-01
/develop-frontend FE-01
```

실제 저장소의 `.claude/skills/`에 해당 스킬이 있는지 확인하고, Task와 스킬의 입력 형식이 일치하도록 작성해 줘. 스킬이 존재하지 않으면 임의로 존재한다고 가정하지 말고 별도 확인 사항으로 기록해 줘.

Task는 구현 및 테스트 완료 후 체크박스를 갱신하고, 검증 결과를 기록할 수 있도록 해 줘.

완료 조건이 일부라도 충족되지 않았거나 테스트를 실행하지 못했다면 해당 Task는 미완료로 유지해야 해.

구현 중 요구사항이나 설계 변경이 필요해지면 관련 문서를 먼저 확인하고, 변경 내용과 영향 범위를 기록한 뒤 반영하도록 해 줘.

## 12. 문서 작성 규칙

모든 응답과 문서는 한국어로 작성해 줘. 기술 용어와 코드 식별자는 필요한 경우 영문을 사용해도 돼.

문서는 Markdown 형식으로 작성하고, 불필요한 줄바꿈을 최소화해 줘. 문장마다 개행하지 말고 관련된 문장은 하나의 문단으로 작성해 줘.

표는 Task 목록, 의존성, 요구사항 추적표처럼 구조화가 필요한 곳에만 사용하고, 같은 설명을 여러 섹션에 반복하지 마.

PRD, 사용자 시나리오, 화면 정의서, 기술 설계서에 이미 정의된 내용을 장황하게 복사하지 말고 관련 ID와 섹션을 참조해 줘.

개발 실행 계획은 **바로 AI가 개발에 착수할 수 있는 수준으로 구체적이되, 코드 구현 내용까지 작성하지 않는 것**을 원칙으로 해 줘.

완료 조건은 모두 미체크 상태로 작성하고, 실제 개발과 테스트를 수행하기 전에는 완료 처리하지 마.

## 13. 작업 진행 방식

다음 순서로 진행해 줘.

1. `.claude/CLAUDE.md`와 `docs/`의 기존 문서를 모두 확인한다.
2. 기술 설계서의 설계 결정, 미결 사항, MVP 범위를 분석한다.
3. 현재 저장소의 코드, 개발 스킬, 서브에이전트 및 MCP 설정을 확인한다.
4. 전체 개발 Task 목록과 의존성을 먼저 제안한다.
5. Task가 너무 크거나 작지 않은지, 중복이나 누락이 없는지 검토한다.
6. 내가 Task 구성과 실행 순서를 승인하면 `docs/5-plan.md`를 작성한다.
7. 최종 작성 후 FR/NFR, SN, SC, TD와 Task의 연결 관계를 검증한다.
8. `.claude/CLAUDE.md`의 문서 상태와 경로를 실제 내용에 맞게 갱신한다.

**지금은 전체 실행 계획서를 바로 작성하지 말고, 권장 Task 목록과 개발 순서, 선행 검증이 필요한 사항부터 제안해 줘. 내가 검토하고 승인하면 최종 실행 계획서를 작성해 줘.**
